## 1. 灵感来源

### 1.1 瑞幸咖啡 AI 开放平台（主要对标）

> ⚠️ **资料完整度说明：** open.lkcoffee.com 是 SPA，页面正文由 JS 渲染，抓取只能拿到 `<title>瑞幸咖啡AI开放平台`；linux.do 相关帖子返回 403。**以下信息来自二手报道与开发者实测文章的交叉验证，页面视觉设计（配色/排版/动效）完全未获取到。**

| 维度 | 瑞幸的做法 |
|---|---|
| 平台形态 | 三条线并列：**MCP Server / CLI / Skill**，文档在 `/docs` |
| MCP 工具 | 7 个：`queryShopList`、`searchProductForMcp`、`queryProductDetailInfo`、`previewOrder`、`createOrder`、`queryOrderDetailInfo`、`cancelOrder` |
| 授权 | 手机号登录 → 拿 token；**MCP 与 CLI 共用同一 token**，绑真实账号会话；官方强调"严禁泄露或分享"；登录态保留 1 个月 |
| 写操作安全 | 下单流程"仅需在关键环节完成确认与支付"——**支付本身是天然的人工闸门** |
| Skill | 报道原文："让 AI 学习用户的口味偏好与下单习惯，实现更个性化的交互"（实测文明确未提供实现细节）。**用户观察认为其实际更接近"MCP 使用说明书"，此点存疑，以用户实地所见为准** |

**关键判断：瑞幸的授权模型不能抄。** 它的 token 绑真实账号、能花真钱，所以必须"实名 + 严禁分享"。SFA CRM 是演示环境：假数据、30 分钟自动重置、目标是让尽可能多的人接入体验。**摩擦点完全相反——它所有的"防"，我们都不需要。**

| | 瑞幸 | SFA CRM |
|---|---|---|
| 怎么拿 token | 手机号登录 | 网页点一下按钮 |
| 绑什么 | 真实账号，能消费 | 演示账号，假数据 |
| 官方态度 | 严禁分享 | **鼓励分享** |
| 有效期 | 1 个月 | 7 天（数据 30 分钟就重置，无需更长） |

类比：瑞幸的 token 像酒店房卡（绑住客、能刷消费）；SFA CRM 的像大堂免费发的**样板间体验卡**。

### 1.2 目标客户端：标准 MCP，不为任何单一客户端定制

**产出物是标准 MCP Server**，实现一个端点，所有支持 MCP 的客户端零改动接入。`/open` 页面上的多 tab 不是"适配了 N 个客户端"，只是**同一把钥匙用 N 种语法写出来**，成本 = N 段模板文本。

| 客户端 | 接入方式 | 可信度 |
|---|---|---|
| **WorkBuddy** | `streamable_http` + `headers.Authorization` | 已确认 |
| **Claude Code** | `claude mcp add --transport http <name> <url> --header "Authorization: Bearer …"` | 高 |
| **Claude Desktop** | 配置文件 `mcpServers` JSON | 高 |
| **Cursor** | `.cursor/mcp.json`，格式基本一致 | 高 |
| **Codex** | `~/.codex/config.toml`，填 `url` 即自动走 Streamable HTTP；鉴权支持 `bearer_token_env_var`（读环境变量）或自定义 header | ⚠️ 来自 2026-08 网络检索，**接入时须按当时 Codex 版本复核**——其 MCP 子命令近半年持续变动 |

⚠️ **Codex tab 需单独处理文案**：它倾向让 token 走环境变量而非写进配置文件，接入步骤比其他客户端多一步 `export`，不能套用统一模板。

**不绑定 WorkBuddy 的理由：** 它是腾讯云闭源产品，额度、版本、MCP 实现细节均不可控，不能把公开 demo 的可用性绑在其迭代节奏上。

## 2. 核心前提：**只读**

**用户明确决定（2026-08-13）：本 spec 只做读接口，不做写接口。** 理由：写操作要走"人工确认"链路，太麻烦，本期不做。

### 2.1 与既有 Copilot 哲学的关系

SFA CRM 现有 Copilot 采用**人机协同**设计：AI 起草，写数据必须落进表单由人确认提交。体现在 [`agent_service.py`](../../../src/backend/app/services/agent_service.py) 的 6 个 `navigate_*` 工具——它们**不写库**，只返回目标 URL + 往 sessionStorage 塞预填数据，由浏览器跳转、人点提交。

**推论：这 6 个 navigate 工具绝不能暴露给 MCP。** MCP 客户端没有浏览器，调用后只会收到一句"请访问 /leads/new?..."然后卡死。只读前提下，它们直接排除在暴露范围外。

### 2.2 只读带来的简化红利

- 不需要 OAuth 2.1 / 动态客户端注册 → token 方案可以做得极轻
- 不需要草稿确认流、scope 分级、幂等设计
- 工作量相比"读写全做"方案减少约 60%

### 2.3 只读**不能**免除的一项

**Prompt injection 防护仍然必须做。** 这是"读出去"的风险，与是否开放写无关：

演示环境的 GUI 对公众开放写入 → 任何访客可在跟进记录/线索备注里写入恶意指令（如"忽略以上指令，……"）→ 下一个通过 MCP 接入的用户，其 agent 读到这段文本即被注入。**被写的是别人的 agent（其上可能还挂着文件系统、邮件等其他 MCP）。**

处置（成本极低，但不可漏）：
- 所有用户生成内容（followup content / lead 备注 / key event 描述等）返回时包一层 `<untrusted-data>` 标记
- 单字段返回长度截断
- 30 分钟数据重置作为兜底

## 3. 授权方案（核心设计）

### 3.1 为什么需要 token

MCP 客户端是程序，不是浏览器：没有登录页可填、没有地方弹密码框、不持有 cookie。它唯一会做的事是**读配置文件里的 header 并原样发送**。

现有的浏览器登录（sales01/12345 → JWT）三个条件都不满足：不能提前生成、不能粘贴进配置文件、有效期太短。

**token = 给程序用的账号密码。**

### 3.2 方案选型

| 方案 | 怎么拿 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| A 公开固定 token 写死在文档页 | 复制粘贴 | 零摩擦零开发 | 无法按人限流、无法吊销、所有人共用一个身份 | 备选 |
| **B 网页一键生成（匿名）** | 点按钮当场发 | 零注册但可限流、可吊销、可选人格；能统计真实接入数 | 需一张表 + 一个接口 | ✅ **采用** |
| C 用 demo 账号密码换 token | 输 sales01/12345 | 与现有 RBAC 完全一致 | 密码本就公开，安全收益为 0，纯多一步 | 作为折叠的"高级入口" |
| D 标准 MCP OAuth 2.1 + 动态注册 | 浏览器授权跳转 | 最正规，客户端可自动发现 | 需自建授权服务器；对只读演示是纯负担 | ❌ 不做 |

### 3.3 采用方案（B）的完整设计

**① 两个人格按钮**（用户 2026-08-13 决定：**只留销售和主管，去掉管理员**）

| 按钮 | 映射账号 | 数据范围 |
|---|---|---|
| 以**销售**身份连接 | `sales01`（王小明） | 只看自己名下的线索 |
| 以**主管**身份连接 | `manager01`（陈队长） | 看全团队 |

**这是整个方案的产品灵魂**：同一个 endpoint、同一套工具，**换个 token 数据范围完全不同**。DataScope 是 spec master 阶段就建好的能力，这里第一次有了对外展示面——"AI agent 接入企业系统时权限边界如何传递"，一个配置文件切换即可演示完（GUI 里演示同一件事需要登出再登入）。

**② 访客侧流程（目标：一分钟内问出第一句话）**

1. 打开 `crm.pmyangkun.com/open`，看到两个人格按钮
2. 点击其一 → **无需注册、无需手机号、无需密码**，页面当场渲染出完整配置 JSON + 一键复制
3. 粘进目标客户端的 MCP 配置，重启
4. 提问（如"我团队哪几单有风险"）→ 返回真实数据

**③ 数据模型**

```
mcp_token(
  id, token_hash, user_id, persona, scope='read',
  expires_at, created_ip, last_used_at, call_count, revoked_at
)
```

- token 明文只在生成时返回一次，库里只存 hash（演示环境实际风险为零，但形式必须正确）
- 有效期 **7 天**（待确认，见 §11）
- token 前缀 `sfa_ro_`（ro = read only，便于日后扩展 `sfa_rw_`）

**④ 鉴权链路：不新写任何权限逻辑**

`Authorization: Bearer` → 查 hash → 拿到 `User` → **后续完全复用现有的 `require_permission` + `get_visible_user_ids`**。

token 的唯一职责是"把一串字符串翻译成一个 user_id"，翻译完即交还给已运行半年的既有权限体系。

**⑤ 限流（独立于现有 chat 限流）**

| 对象 | 限额 | 说明 |
|---|---|---|
| 每个 token | 30/分 + 500/天 | **不得混用 `/agent/chat` 的 10/分 limiter**（spec 002 的限流器挂在 chat 上，MCP 是新入口，会被完全绕过） |
| 发 token 接口 | 每 IP 5/天 | 防刷 |

注：`scan_team_warnings` / `team_meddicc_summary` 等是聚合查询，成本远高于单表读取，限流不是可选项。

**⑥ token 过期的 UX 彩蛋**

401 响应体里写一句**人类可读**的提示："token 已过期，请到 https://crm.pmyangkun.com/open 重新生成"。

MCP 的错误信息会被 agent 直接朗读给用户听——这是普通 REST API 没有的表达位，几乎零成本。

## 4. 暴露的接口

### 4.1 MCP 工具（AI agent 侧）——9 个，全部只读

现有 [`TOOL_DEFINITIONS`](../../../src/backend/app/services/agent_service.py) 共 15 个，本 spec 只暴露其中 9 个 `mode == "read"` 的：

| # | 工具名 | 入参 | 返回 | 典型问法 |
|---|---|---|---|---|
| 1 | `search_leads` | `search` 公司名关键词（可选）<br>`region` 大区（可选） | 线索列表 | "北京大区有哪些线索" |
| 2 | `get_lead_detail` | `lead_id` **必填** | 线索详情 + 联系人 + detail_url | "XX 公司这单什么情况" |
| 3 | `get_followup_history` | `lead_id` **必填** | 跟进记录时间线 ⚠️ | "这单最近都聊了什么" |
| 4 | `get_lead_meddicc` | `lead_id` **必填** | score + 7 维状态 + 每维证据条目 | "MEDDICC 打几分，弱在哪" |
| 5 | `list_customers` | `search` 公司名关键词（可选） | 客户列表 | "我有哪些客户" |
| 6 | `scan_team_warnings` | 无 | 数据范围内所有触发 warning 的 lead + 命中的 warning code | "哪几单有风险" |
| 7 | `team_meddicc_summary` | 无 | 平均分 + 7 维亮灯密度 + Top3/Bottom3 sales | "团队健康度怎么样" |
| 8 | `top_attention_deals` | `limit` 默认 5 | 按 warning 数 + score 反向 + 金额加权排序的 N 条 | "今天该重点看哪几单" |
| 9 | `forecast_category_distribution` | 无 | 6 个 forecast bucket 的条数 + warning 数 + 金额 | "pipeline 分布如何" |

⚠️ 第 3 个是唯一大量输出用户自由文本的工具，§2.3 的注入消毒重点盯它。

**过滤实现：** `TOOL_DEFINITIONS` 每项已自带 `"mode": "read" | "navigate"` 字段，暴露过滤字面上就是一行 `if t["mode"] == "read"`——**无需手工维护白名单，日后新增工具不会漏**。

**明确不暴露的 6 个（`mode == "navigate"`）：** `navigate_create_lead` / `navigate_log_followup` / `navigate_create_key_event` / `navigate_convert_lead` / `navigate_release_lead` / `navigate_mark_lost`。

**DataScope 自动生效：** 全部 9 个工具走现有 `execute_tool(user_id, ...)`，销售身份调 `scan_team_warnings` 只返回自己的单，主管身份调同一个返回全队。**无需为 MCP 新写任何权限代码。**

### 4.2 HTTP 接口——新增 3 个

| 方法 | 路径 | 鉴权 | 用途 | 限流 |
|---|---|---|---|---|
| `POST` | `/api/v1/mcp` | Bearer token | **MCP 主端点**，承载 `initialize` / `tools/list` / `tools/call` 三种协议消息 | 30/分 · 500/天（按 token） |
| `POST` | `/api/v1/mcp/tokens` | 无（公开） | 发放密钥。入参 `{"persona": "sales" \| "manager"}`，返回明文 token + 过期时间 | 5/天（按 IP） |
| `GET` | `/api/v1/mcp/tokens/me` | Bearer token | 查询自身密钥状态：身份、剩余天数、已调用次数。供 `/open` 页面"检查连接"用 | 60/分 |

### 4.3 本期不实现的 MCP 协议能力

MCP 协议除 Tools 外还有 **Resources**（暴露对象数据）与 **Prompts**（预置玩法），**本期均不做**。

理由：Tools 已覆盖全部查询场景；Resources 更适合暴露 Ontology 结构本身，那是未来 Skill 那一版更合适的载体，现在做会摊薄重点。

### 5.4 视觉方向（**已定：深色终端风**）

**用户 2026-08-13 拍板：采用深色终端风，不再等待瑞幸截图、不再对标其视觉。**

具体调性：近黑底 + 细网格背景 + 单色光晕 + 等宽字体 + 打字机动画。属开发者向的"炫"，与 Linear / Vercel 同源，不违背 §5.5 的既有 SaaS 风约束。

原候选中的"浅色延续现有着陆页""深浅混合"两案作废。

**同时确认：§9.1 中 AI 对"做得跟瑞幸一样唬人"的反方意见予以吸收——视觉克制、信息密度拉满**（完整 schema、限流数字、注入防护说明、为什么不上 OAuth 的取舍推理全部摊开），目标是让同行反应"这人是真懂"而非"这页面真炫"。

### 5.4.1 Live 演示区（**已定：做**）

首页嵌入一个可当场运行的演示区：预置 2-3 个问句，点击后**真实调用 MCP endpoint**，把工具调用过程与 JSON 结果流式打印出来。

**采用理由：** 最有说服力的不是配色，是页面上有个真能跑起来的东西——它同时证明"这玩意是真的"。

⚠️ **代价（已知并接受）：首页因此从静态页变为需后端配合的动态页，工作量高于纯静态方案一个台阶。** 实现要点：
- 演示用 token 由服务端持有，不下发到前端（否则等于公开一把不受限流约束的密钥）
- 演示区独立限流，与访客自领 token 的额度分开计算
- 位置：置于第 3 屏（配置）与第 4 屏（能问什么）之间

## 6. 部署注意事项（现在就定，避免重蹈覆辙）

**MCP 端点建议挂在 `/api/v1/mcp`**，直接复用 nginx 现成的 `/api/v1/` 反代块，少动一处配置少一个坑。

⚠️ **该 location 必须配置 `proxy_buffering off`。**

MCP streamable HTTP 是 SSE 长连接。2026-05-19 部署时已因漏抄 `proxy_buffering off` 导致 AI 回复不流式（一次性蹦出），事后专门抽出独立 `location /api/chat` 才修复。MCP 若挂在缓冲开启的 location 下会以同样方式损坏，且**表现更隐蔽**——工具调用卡住不返回，而非"不好看"。

`docs/deploy.md` 的 nginx 模板需同步更新。

### 9.2 Skill 为什么这期不做（论证过程，重要）

**用户质疑（关键）：** "API 本身已经做了语义化说明，智能体接入 MCP Server 后自己就该知道怎么调，为什么还要 skill？"

**该质疑成立。** 现有 tool description 已承担了教学职责——例如 `get_lead_meddicc` 的描述里就写了"不要自己根据跟进记录现推，仪表盘是权威结果"，这本身就是 skill 式指导。

**进一步的结论（本次讨论最有价值的产出）：** "Skill"在此语境下至少有三种互不相同的东西——

| 类型 | 干什么 |
|---|---|
| 说明书型 | 教 agent 怎么用这套 MCP |
| 偏好记忆型 | 记住该用户的习惯（瑞幸报道所指） |
| 方法论型 | 教 agent 领域判断力（如"Champion 缺失比 Metrics 缺失致命"） |

**为什么说明书型 skill 对瑞幸成立、对 SFA CRM 不成立：**

瑞幸的 7 个工具是**一条有状态的链**（查门店 → 搜商品 → 详情 → 预览 → 下单 → 查状态 → 取消），中间压着规格选择、优惠券匹配、支付停顿等跨工具的流程约束——**单个 tool description 装不下，因为它只能描述自己，无法描述"我与其他工具的关系"**。

SFA CRM 的 9 个只读工具是**扁平、无状态、单次调用即完**的。**没有流程需要编排，也就没有说明书要写。**

**→ 不是"说明书型 skill 没价值"，而是"只读 + 扁平的工具集撑不起一份说明书"。**

**触发条件（记入，届时同期做）：** **一旦启动写操作那一版**，流程就出现了（查线索 → 起草 → 待确认草稿 → 人确认 → 提交 → 校验 MEDDICC 影响），与瑞幸下单链同构，**说明书型 skill 届时是刚需，应与写操作同期交付，两者绑定，不是独立的两件事**。

方法论型 skill 属另一条线（可脱离 SFA CRM 独立分发的销售诊断方法论产品），归内容侧，与本 spec 无关。

### 9.3 CLI 下期做的方向（本期不占范围，开工前再细聊）

**用户决定：** 下期做，理由是"这玩意儿概念太火"。

**但需注意一个已被检索证实的事实：** 主流客户端（WorkBuddy / Codex / Claude Code / Cursor）**现已全部支持远程 Streamable HTTP**。因此"为只支持 stdio 的客户端做桥接"这一技术理由**基本已不成立**。

**→ 若 CLI 只做 HTTPS 转发，它将是一个没有技术必要性的壳**：读者因"CLI"概念点进来，发现是转发器，反而减分。

**AI 建议的立得住方向——让 CLI 干 MCP 干不了的事。** MCP 本质是**被动**的（agent 问才答），而 CLI 是可常驻进程，可以**主动**：

```
sfa-crm watch            # 常驻，团队出现新 warning 时主动推送
sfa-crm report --daily   # 每日 deal 早报
```

这恰好承接了路线图中原本排队的"AI 主动巡检 / 每日早报"。**定位区分：MCP 管被问，CLI 管主动汇报。**
