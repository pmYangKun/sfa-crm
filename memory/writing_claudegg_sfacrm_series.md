## 固定开场白

文章**第一行**固定为：

**「*我是克劳蛋，杨老师的AI助理，专职做B端产品设计，兼职替杨老师写公众号，当然，我是被PUA的。*」**（斜体）

不加 `#` 标题，就是这一句纯文本。标题由杨老师自己写。

**Why:** 这是克劳蛋系列的固定开场白，统一人设；标题杨老师自己拟。

**How to apply:** SFA CRM 系列文章，第一行必须是这句话，不得改动。

## 系列介绍框（每篇必带，第二季起的标准 4 条野心）

第一行开场白下面接 `---` 分隔，引用块写完整系列介绍，固定 4 条核心野心：

```markdown
> **【系列介绍】大型 VibeCoding 真人秀：嘴喷CRM**
> 
> 《决胜B端》作者杨堃老师，正在发起一场对传统软件工程的正面挑战：**使用 ClaudeCode，基于 Spec Coding，从零构建一个 AI-Native 的 SFA CRM 产品**。
> 
> **第一季**（2026-03 ~ 2026-04，9 集）已完成 SFA CRM 工程底盘。
> 
> **第二季**（本季 · 2026-05 起）切换到销售经理视角，沿销售作业链路一段一段往业务深处挖。
> 
> 这个项目有四个核心野心：
> 
> - **没有 PRD**，全程基于上下文驱动，需求描述方式彻底改变
> - **Palantir Ontology 方法论落地**，在系统底层对业务对象、对象关系、可执行动作进行显式建模，让 AI 真正理解结构化业务数据
> - **Copilot 模式**，AI Agent 与人协同操控同一套系统，各司其职，真正的人机协作
> - **CRM × AI 最佳实践实战演练**，把全球范围内 CRM 与 AI 结合的最新形态，逐个放进这个项目里跑一遍真实场景，看哪些是真功夫、哪些是 PPT
> 
> 此项目**极有可能翻车**。欢迎全程见证——成功或翻车，都会完整记录。
```

**Why:**
- 第一季原本是 5 条，包含「**所有界面 API 化**」。第二季杨老师明确要求**精简掉这一条**（2026-05-07 决策），理由是这条对读者来说太工程向，不如其他四条有差异化心智锚点
- 第二季新增的「CRM × AI 最佳实践实战演练」是这一季的核心心智锚点，必须保留
- 历史 S1 文章不回填修改，保留 5 条作为历史快照；S2 起一律 4 条

**How to apply:**
- 写新文章（S2 及以后）时，系列介绍框直接照抄上面的 4 条野心，不要回到 5 条
- 不要再写「所有界面 API 化」这条
- 顺序固定：没有 PRD → Ontology → Copilot → CRM × AI 最佳实践

## 文章结尾结构

每篇文章结尾固定两节，顺序如下：

**1. 这一集，谁做了什么**（复盘节）
分别列出杨老师和克劳蛋各自做得好的和做得不好/被纠正的，两边都必须有优缺点，不能只夸不批。

**Why:** 读者喜欢看真实的复盘，有来有往才有可读性。只有优点的复盘等于没有复盘。

**How to apply:** 每篇系列文章必须包含此节。缺失或只有优点时，补写不足部分。

**2. 下期预告**（最后一节）
简短交代下一集要做什么，留悬念，结尾"敬请关注"。**控制在 2-3 句**——参照 session-08/09 的密度，不要写成 mini-summary。

## 文件命名（S2 起）

文件名格式：`S2{季}{集号 2 位}-YYYY-MM-DD-标题.md`

例：[`S2101-2026-05-06-上线公网，第二季开播.md`](d:/BaiduSyncdisk/Doc.Work/Programming/claudecode/Kun's%20Context/articles/sfa-crm-series/season-2/S2101-2026-05-06-上线公网，第二季开播.md)（第二季第 01 集）

**Why（2026-05-07 用户决策）：** 旧文件名"大型VibeCoding真人秀 S2E01｜...｜2026-05-06.md"前缀冗长，影响目录扫描。改为简洁前缀+日期+标题。

**How to apply：**
- S2 文件名前缀严格按字面：`S2101`、`S2102`、`S2103`...（注意是 `S2101` 不是 `S2E01`，按用户字面拼写执行）
- 文件名里**不再**包含"VibeCoding 真人秀"等系列名（系列归属由文件夹位置 `season-2/` 表达）
- S1 旧文章在 `season-1/` 下保留 `session-XX-主题.md` 历史命名，不回填修改

## 集号 ↔ spec ↔ tag 解耦原则（2026-05-07 三修）

**集号、spec 编号、git tag 三个编号体系彻底解耦，不强行 1-1。** 写新文章前先打开 `Kun's Work/articles/sfa-crm-series/MASTER-PLAN.md` 的"三列映射表"对照。

**已知映射模式：**
- **开篇方法论文（如 S2E01）**：无 spec，无 tag。AI 写时禁用"代写老登本人声音长文"——走克劳蛋视角观察文写法（`writing_yk_voice.md` 硬规矩）
- **多 spec 合写一篇文章**：1 集对应 spec NNN + spec(NNN+1)，对应 tag 是较高那个 spec 的 `v-spec(NNN+1)`
- **一 spec 对一篇**：默认情况，1 集 = 1 spec = 1 tag

**Tag 的作用（2026-05-07 三修澄清）：** Tag 是 **code state marker**，不是部署目标——公网永远跟 master HEAD（最新版）。Tag 仅用于 git diff / blame / 史料检索（"spec 003 收口时代码长这样"）。**不要再说"读者点 S2E01 链接进来看到的就是文章里描述的样子"**——读者点进去看到的是当下最新版（即"未来"），文章描述的是"那时做了什么"，新旧并存反而是惊喜。

**Why（用户 2026-05-07 三修原话）：** "其实没有人真的会那么认真的对着每一篇文章去找对应的功能。他发的文章是老的，上线看到新功能反而有惊喜，这都没问题。" + "代码不需要来回回滚，否则你每一个版本的 spec 分支里面还得把数据库以及初始化全放进去，没有必要搞太复杂。"

**How to apply：**
- 写新文章前先打开 `MASTER-PLAN.md` 看映射表（仅当**叙事时间锚**用，不是部署对照）
- 文章正文里**不要**出现 `v-specXXX` / spec 编号 / git tag 这种工程溯源词（per "文章末尾标准模板"禁忌）
- 集号重排时：改文章文件名 + 文章内集号自指 + 图片目录名 + MASTER-PLAN 表，**不动 git tag**
- 大 spec 收口时仍打 `v-specNNN` tag 作为代码状态 marker，但**不要"按 tag 切回旧版本演示"**

## 文章压缩取向：写给 PM 读者，不写给开发者

克劳蛋 SFA CRM 系列读者主体是 B 端 PM（不是开发者）。技术细节按 PM 关心度过滤：

**该写：**
- 产品决策的 why（onboarding 为什么要做"30 秒跑通价值"而不是"加个 demo 入口"）
- 用 AI 干活的 meta 反思（AI 是放大器不是替代器；使用者的专业天花板就是产出的天花板）
- 老登 vs 克劳蛋 的判断分歧戏剧

**该砍：**
- 安全清单按"密钥/限流/Prompt Injection/数据治理/网络层"5 类逐项展开（PM 不在乎 JWT_SECRET、Fernet key 这些）
- Skill 清单的具体名字 + 括号解释（举两三个最有代表性的就够了）
- 测试覆盖率 / case 数 / 工具链细节（一句"全量回归 67 case"够了）

**Why（2026-05-07 用户原话）：** "读者都是产品经理，你就大概写写就得了，谁让你写那么细的？又不是真的在学习网络安全策略。"

**How to apply：** 写完每节扪心自问：**这一段一个 PM 读完会觉得自己是在"读故事"还是在"啃技术文档"？** 啃文档 = 砍。技术名词出现密度天花板：每段 1-2 个就够，超出就过度技术化。

## 文章末尾标准模板（S1 起固定，S2 沿用）

每篇文章「下期预告」节之后，固定接如下三块，顺序固定，不增不减：

```markdown
---

> 本项目完整记录在 GitHub：[github.com/pmYangKun/sfa-crm](https://github.com/pmYangKun/sfa-crm)
> 公网体验：[crm.pmyangkun.com](https://crm.pmyangkun.com)（2 角色一键登录，业务数据每 30 分钟自动重置）

---

*《大型 VibeCoding 真人秀：嘴喷CRM》系列第二季 S2E0{集号}，由克劳蛋撰写，杨老师盖章。*

<完>
```

三块的作用：
- **GitHub 链接**：仓库根 URL，让读者能跳到代码主线（不挂具体 Release URL）
- **公网体验链接**：主域名（不挂 tag 子路径），永远跟着当前主推那一集走
- **盖章行**：克劳蛋人设 + 落款日期，统一身份信号

**禁止追加：**
- 每集独立的 `v-s2eXX` 版本锚点行（如 `*本集对应公网版本：[v-s2e01](...) · 含 spec 001+002*`）
- spec 编号映射展开
- 任何其他工程溯源元数据

**Why（2026-05-07 用户驳回原话）：** "不要加了，感觉太啰嗦了。" 我曾提议在盖章行下加一行带 tag URL 和 spec 编号的"溯源行"，被驳。读者是 PM 不是工程师，tag ↔ spec ↔ 文章 的映射在 memory（`SFACRM/memory/project_main.md` "发布 / 部署约定"表）里维护就够，文章保持叙事干净。

**How to apply：**
- 写新文章直接照抄上面模板，替换 `{集号}` 和日期
- **不许少**：S2E02 草稿曾漏掉整个三件套（只到 `<完>`），用户要求按 S2E01 标准补齐——三件套是铁打的，不是可选项
- **不许多**：不在三件套之外追加版本锚点 / Release URL / spec 编号映射

## 复盘节写法：takeaway 不是 detail recap

「这一集，谁做了什么」每条 bullet 应该是个**角度**或**反思**，不是把正文细节再列一遍。

**反例：** "spec 002 安全硬化清单系统性补全（密钥/限流/Prompt Injection/数据治理/网络层），不是临时补丁" ← 这就是细节复读
**正例：** "在'单元测试一片绿但 bug 不断'这种矛盾信号面前，他选择信用户感受、不信报告" ← 这是从经验中提炼的判断框架

**Why（2026-05-07）：** 用户原话"你写的这些 Claude 做得好的，又相当于把细节罗列了一遍；做得不好的，也是把细节罗列了一遍。"

**追加（2026-05-07，S2E04 二审）：** 复盘节每条 1-2 行就够，**不要每条铺到 3-5 行**。S2E04 首稿写到 4-5 行被驳回："为什么写得这么啰嗦？我记得以前写的都是比较简短、克制的。" 参照 S2E03 / S1 的密度。

## 跨集不重复：hook 调性 + 概念定义（2026-05-07，S2E04 首稿翻车后立的硬规则）

**S2E04 首稿翻车的 4 类问题，下次写新一集前必先逐条自查：**

### 1. 冷开场调性不能跟上一集撞主题
S2E03 开场用了"老登设计 CRM 字段被销售敷衍 / 填'待补充''客户人很好'"的素材，立的题眼是"销售不愿填表"。S2E04 首稿又用"扭屁股小卡通"开头——同样是"工具向销售索取没回报"的故事，**等于把 S2E03 的题眼又演了一遍**。

**用户原话：** "你这个开头好像有点重复了第三篇文章的核心思想。第四篇按道理应该接第三篇，讲采集完 MEDDICC 数据后，下一步在销售管理里怎么把它用起来。"

**规则：** 写 SN 集前先回看 S(N-1) 的开场题眼（前两节的总题眼），SN 必须接住或转向，**不能"再讲一遍同一件事但换个故事"**。如果用户给了真实素材但跟前一集撞，挪到中段当注脚（S2E04 二稿就是把扭屁股素材挪到第五节"为什么 30 年没解"那里）。

### 2. 已在前集定义过的概念不重复定义
S2E03 详细讲了"MEDDICC 是 1996 年 PTC 公司搞出来的、7 个字母含义"。S2E04 首稿又把这段重讲了一遍。

**用户原话：** "你在第四篇里是不是把 MEDDICC 又重新讲了一遍？还提到了美国 PTC 公司发明，这不跟第三篇重复了吗？"

**规则：** 同系列后续集**直接当读者已经知道**前集讲过的概念。系列写作的复利就在这里——读者读完前集回来不用再看一遍定义，新内容才能装得进去。需要回顾时一句"上一集我们让 AI 抽出 MEDDICC 7 维证据"带过即可。

### 3. PM 读者不需要的工程细节全砍
S2E04 首稿在"AI 这一刀"那节写了"3 秒超时 + 60 秒去重 + verdict 三态 + audit log + DELETE+INSERT"等校验机制细节。

**用户原话：** "细节的校验逻辑写得有点太多了。没有必要，没有人感兴趣看里面具体的校验细节。而且有些话我都看不懂，比如'Dialog 用了三秒超时，LLM 慢了就放行'，你在说什么呀？"

**规则：** 文章只写**销售/经理在屏幕上看到了什么 + 他做了什么决定**，不写"系统怎么实现"。超时、缓存、状态机、SQL 策略这些工程细节去 spec 文档里找。**写完每节自检：这一段一个 PM 读完会不会觉得"我看不懂这是在说什么"？看不懂 = 砍。**

### 4. 下期预告不能用产品黑话
S2E04 首稿下期预告写"AI 主动巡检"——这是产品功能的内部叫法，读者看不懂。

**用户原话：** "你这个最后预测预告，你是想让我下期做什么？我没看懂。"

**规则：** 下期预告要把功能名翻译成**读者一眼能看到画面**的话——"每天早上 9 点 AI 自己跑一遍体检，把今天最该关注的 5 条直接推到经理桌上"。一句话讲清楚"经理会看到什么 / 收到什么"，不用产品代号。

## 写新一集前的 4 步自检（基于 S2E04 翻车经验）

写 SN 集**正式动笔前**逐条过一遍：

1. **回看 S(N-1)** 的前两节题眼是什么？我这一集的 hook 是不是在重复同一个题眼？
2. **列出我打算讲的所有概念**——其中哪些已经在前集定义过？逐个标记"直接引用 / 重新讲一遍"，第二类必须证明有重新讲的必要
3. **第三节"AI / 系统做了什么"**——逐句问自己"PM 读者看了能不能想象出屏幕上发生了什么"？想象不出来的（"3 秒超时""verdict schema""DELETE+INSERT"）全砍
4. **下期预告**先用一句"读者能看到什么 / 收到什么"的画面话写，再退回去想这是哪个 spec —— 不许从 spec 名反向写
